# Multi-terminal edges: decision record

Every decision behind edges with terminals, with its date and the test that checks
it. The implementation follows this record and the README section *Edges with
terminals*; a deviation is proposed and decided here first, never built in
quietly. Each implementation stage lists in its pull request which entries it
touches and how their tests came out.

| # | Decision | Decided | Checked by |
|---|----------|---------|------------|
| D1 | **Edges are first-class.** An edge is its list of terminals, in the C core as well: no auxiliary node, no replacement edge, no star expansion. The algorithms work on terminal incidence (node → its (edge, terminal) pairs, edge → its terminals). | 2026-10-30, reaffirmed 2026-10-31 | `test_multi_terminal_graph_holds_exactly_the_given_nodes_and_edges` (internal node and edge counts equal the given ones) |
| D2 | An edge is a tuple of node ids: a pair is a two-terminal edge, a longer tuple an edge with that many terminals, the position is the terminal index. Terminals are addressed as `(edge_index, terminal_index)`, never by node. | 2026-10-31 | `test_terminal_index_is_the_position_in_the_tuple`, `test_two_terminals_at_one_node_stay_distinguishable` |
| D3 | **Graphs of two-terminal edges behave exactly as before**: every existing call, input format and result keeps its meaning and its speed, except membership with both endpoints masked (D18). | 2026-10-31 | the existing unit and integration suites unchanged; instruction counts of all existing scenarios against `main` within layout noise |
| D4 | Directed: `(u, v)` stays an edge from `u` to `v` with no extra input; a multi-terminal edge is `(in-nodes, out-nodes)`, terminal indices run through the in-nodes first; every edge has at least one in-terminal and one out-terminal. | 2026-10-31 | `test_directed_pair_keeps_its_meaning`, `test_directed_multi_terminal_needs_an_in_and_an_out_terminal` |
| D5 | Directed reach is **OR**: reaching any active in-terminal reaches every active out-terminal. AND semantics is out; it would be a separate edge type if ever needed. | 2026-10-31 | `test_one_active_in_terminal_reaches_every_out_terminal` |
| D6 | **One rule decides activity:** a terminal is active iff its edge, the terminal and its node are unmasked. Every algorithm asks only this rule. | 2026-10-31 | the twelve masking-case tests (D9) on every algorithm family |
| D7 | Connection: an edge joins all of its active terminals (directed: every active in-terminal to every active out-terminal). | 2026-10-31 | masking cases 2, 3, 8 |
| D8 | **Membership** (user rule): an edge belongs to a component iff all of its active terminals are at nodes of that component; with no active terminal it belongs to none. | 2026-10-31 | masking cases 1–6, membership column |
| D9 | The twelve masking cases of the README table, each with a named test, connection and membership. | 2026-10-31 | `test_masking_case_<n>_<name>` for n = 1…12 |
| D10 | Masks are chainable views: `without_edges`, `without_terminals`, `without_nodes`; they combine as a union, order does not matter. | 2026-10-31 | `test_masks_combine_as_a_union_in_any_order` |
| D11 | Weights: one per edge for graphs of two-terminal edges, as before; one per terminal as soon as an edge has more than two terminals. Passing through an edge costs the entry terminal's weight plus the exit terminal's weight. | 2026-10-31 | `test_path_through_a_multi_terminal_edge_costs_entry_plus_exit`, D3 |
| D12 | An undirected edge may have one terminal (joins nothing, belongs to its node's component); a directed edge has at least two. | 2026-10-31 | `test_single_terminal_edge_joins_nothing_and_belongs_to_its_node` |
| D13 | Pair-based methods (`bridges()`, `edge_indices(u, v)`) keep their meaning on graphs of two-terminal edges and raise, naming `critical_edges()` and `edge_indices_at()`, on a graph with a multi-terminal edge. `*_with_branch_ids` stay as they are. `edge_indices_at(node_ids)` matches the set of terminal nodes (edge case 16). | 2026-10-31 | `test_pair_methods_raise_on_multi_terminal_graphs`, `test_edge_indices_at_finds_edges_by_their_terminal_nodes`, D3 |
| D14 | A tree-shaped edge with k terminals is **one** biconnected block holding its k terminal nodes. | 2026-10-31 | masking case 12 |
| D15 | Scope of the first pull request: the graph core including directed edges (storage, connectivity, masks, critical edges and nodes, blocks, weighted paths). The contraction logic (reduction with terminal partitions) is the next pull request. | 2026-10-31 | — |
| D16 | pygraphc stays domain-agnostic: it knows terminals by index only; what a terminal stands for is the caller's mapping. | 2026-10-31 | no domain terms in the API (review) |
| D17 | **One fast kernel per algorithm.** One adjacency list whose entries are either a neighbor node (a two-terminal edge, as before) or `-1 - e`, a reference to edge `e` with three or more terminals, whose terminal list is expanded once per traversal. It replaces separate kernels for two-terminal and multi-terminal edges: graphs of two-terminal edges keep their speed, mixed graphs avoid the indirection for their two-terminal edges. Measured on a BFS prototype at 1M nodes: two-terminal graph 29–34 ms against 30–31 ms for the old kernel, mixed graph 44–48 ms against 94–98 ms for a terminal-only kernel, one edge with 1M terminals linear. | 2026-10-31 | instruction counts of every two-terminal scenario against `main` within noise; complexity tier on the multi-terminal shapes |
| D18 | **The membership rule holds for every graph** (user decision): on a graph of two-terminal edges too, an edge with both endpoints masked has no active terminal and belongs to no component; before, its branch id formed a component without nodes. The one change to D3. | 2026-10-31 | `test_view_cc_with_branch_ids_exclude_both_nodes`, `test_two_terminal_edge_with_both_ends_masked_belongs_to_no_component` |
| D19 | **One `Graph` and one `GraphView`** for every kind of edge (user decision): terminal masks and terminal counts exist on every graph (edge `e` of a graph of two-terminal edges has terminals `2e` and `2e + 1`). Methods not yet on terminals raise `NotImplementedError` on a graph with a multi-terminal edge (the C kernel refuses it) or a view with a terminal mask (one `None` test in the view method), so graphs of two-terminal edges pay nothing per call. | 2026-10-31 | `test_masking_case_5_on_a_graph_of_two_terminal_edges`, `test_methods_of_later_stages_refuse_a_terminal_mask_on_two_terminal_edges` |
| D20 | **Edge case behavior is up for discussion** (user decision): every answer that could reasonably go another way is listed in the README section *Multi-terminal edge case behavior*, pinned by `tests/unit_tests/test_multi_terminal_edge_cases.py`, and every test depending on one carries the marker `multi_terminal_edge_case`. A change starts with its test. | 2026-10-31 | `pytest -m multi_terminal_edge_case` |
| D21 | **Negative terminal weights** (user decisions): allowed when every pass costs at least 0 (every two terminals, directed every in-terminal and out-terminal, sum to at least 0), else `ValueError`; no pass leaves through its entry terminal; no second pass of an edge right at its negative terminal after leaving through it. A path may come back to that node another way (edge cases 19 to 22). Before, a path could U-turn through a negative terminal. | 2026-10-31 | `test_edge_case_19` to `test_edge_case_22`; a reference search over explicit passes agreed on 12,000 random graphs and 3,000 masked ones |
| D22 | **One attachment of an edge to a node is a *terminal*** (user decision): the draft called it a *port*, but a port usually means a pair of terminals, so a "two-port edge" would have read as an edge with four terminals. The renamed API: two-terminal and multi-terminal edges, `(edge_index, terminal_index)`, `without_terminals`, terminal masks, per-terminal weights, `terminal_count`. In graph theory (Steiner problems) *terminal* also means a node to preserve; the reduction therefore says *preserved nodes* since #46, so the word has one meaning here. | 2026-10-31 | the renamed tests; no *port* left in the API |
| D23 | **Directed algorithms on multi-terminal edges** (user decision): on the OR rule (D5), a multi-terminal edge is a search state between its active in-terminals and its active out-terminals, never in a result. Strongly connected components: nodes that reach each other through such passes. Topological sort: every active in-terminal node before every active out-terminal node; a cycle raises `ValueError`, also an edge with an in- and an out-terminal at the same node. DAG longest path: a pass counts 1 unweighted and weighs entry plus exit with one weight per terminal (D11). An edge without an active in-terminal passes nothing (case 9). Graphs of two-terminal edges keep their exact results: one kernel each, instantiated with and without multi-terminal edges (D17); topological sort and longest path now run Kahn's algorithm on the CSR adjacency instead of linked lists built per call (25% faster), which also replaces the separate masked copy. | 2026-11-01 | the step C tests in `test_multi_terminal_edges.py`, edge cases 23 to 25 |
| D24 | **Neighborhood queries follow the community** (user rule: align with public opinion; where it splits, Claude decides and lists the case). An edge counts at a node when its terminal there is active and it joins it to another active terminal: any other terminal undirected, an out-terminal from an in-terminal (forward star of Gallo et al., 1993) or an in-terminal from an out-terminal (backward star). `neighbors` / `successors` / `predecessors` are the other joined terminal nodes, the node itself left out (XGI, HyperNetX); `degree` / `out_degree` / `in_degree` / `degrees` count the joined terminals at the node, which equals XGI's edge count wherever an edge reaches a node once and NetworkX's count for self-loops; the `*_edge_indices` list each such edge once. One kernel over the adjacency entries for every query; `degrees` passes over the terminals once. Graphs of two-terminal edges keep their exact results (checked on 3000 random graphs against main). | 2026-11-01 | the step D tests in `test_multi_terminal_edges.py`, edge cases 26 and 27 |
| D25 | **`cycle_basis` returns Berge cycles** (research: the hypergraph consensus). A cycle passes through an edge from one active terminal to another and uses each node and edge at most once; the basis spans the cycle space of the incidence graph, so it holds terminals − nodes − edges + components cycles (m − n + c on two-terminal edges). One BFS over the nodes and one state per multi-terminal edge with at least two active terminals; edge states are left out of the returned node lists. A self-loop and an edge with two terminals at one node give `[node]`. Graphs of two-terminal edges keep their exact results. The signed form (one entry per pass) stays a separate, queued function. | 2026-11-01 | the step D cycle tests in `test_multi_terminal_edges.py`, edge cases 28 to 30 |
| D26 | **Parallel edges and rebuilt views follow the community** (user rule: align with public opinion; where it splits, Claude decides and lists the case). Two edges are parallel when their terminals sit at the same nodes (XGI's duplicate edges), compared as multisets and, directed, per side (case 31); `is_multigraph` reads the C terminal list, so it now also answers for graphs built from `src`/`dst`, where it always said False, at the same or lower walltime (850–912 vs 918–928 ms on 2M edges). `with_edges` takes edges of any number of terminals and keeps the view's terminal mask, the added terminals following the base ones. `split_node` moves terminals, as node splitting divides a node's incidences: an edge index moves every terminal of the edge at the node, so a self-loop now moves whole (before: its first end only), and `terminals_to_new_node` moves single terminals (case 32); a rerouted edge keeps its masked terminals. `Graph.split_node` delegates to the view, one implementation. | 2026-11-01 | the step D part 2 tests in `test_multi_terminal_edges.py`, edge cases 31 and 32 |
| D27 | **`bcc_edge_labels` labels the blocks of D14** (research: in hypergraph block theory every edge lies in exactly one block). The labels are a sixth mode of the one Tarjan search, which replaces the separate edge-label Tarjan; an edge whose active terminals sit at one node gets -1 like a self-loop (case 33). Graphs of two-terminal edges keep their exact labels (checked on 3000 random graphs against main); a two-terminal link is its own edge and is stored once. Every mode now runs in its own non-inlined search: inlined together into `tarjan_entry`, adding the label mode cost bridges 4.6% on GCC 13 (x86-64); separated, bridges count 7.0%, critical nodes 3.9% and edge labels 0.6% fewer instructions than main (CI's toolchain, Ubuntu 24.04). | 2026-11-01 | the step D part 2 tests in `test_multi_terminal_edges.py`, edge case 33 |
| D28 | **`all_edge_paths` reports edge sequences** (research: the literature defines Berge paths, alternating distinct nodes and edges; no library enumerates them). A path enters an edge at an active terminal and leaves at another (directed: an in-terminal to an out-terminal, D5), as D21 and D24 read a pass; the result names edges only, so each edge sequence is reported once even when several node paths realise it (case 34). Terminals of one edge at one node lead to the same node, so a flag table built once per call (O(terminals)) lets only the first active one per node and side enter or leave, which keeps a wide edge linear; a set removes the remaining repeats, on graphs with multi-terminal edges only. Known cost: when consecutive edges share two or more nodes (a ladder) the search walks every node choice, 2^rungs node paths for one sequence; a search over the sets of nodes a sequence can end at would avoid that for `node_simple=False`. One kernel, instantiated per value of `has_multi_terminal_edges` (D17), each instantiation in its own non-inlined function (inlined together, the two-terminal search cost 6% more instructions on GCC 13); graphs of two-terminal edges keep their exact results and order (3000 random graphs against main) at +0.9% instructions on the lattice scenario and -1.0% on the path-enumeration workflow, mostly the new check of every path entry for a failed allocation. | 2026-11-01 | the step D edge path tests in `test_multi_terminal_edges.py`, edge case 34 |

## Implementation notes

Choices inside the decisions above, recorded so that they can be questioned.

| Note | Serves |
|------|--------|
| **Resolved by D17.** Stage 1 kept the multi-terminal kernels in their own extension, `pygraphc._terminals`, because inside `_core` they changed how link-time optimization inlined the shared union-find, costing graphs of two-terminal edges 1 to 3% in the component kernels. The unified kernels (one always-inline source per algorithm, instantiated per value of `has_multi_terminal_edges`) do not have that effect, so `_terminals` is gone: `_core` parses graphs with multi-terminal edges and runs BFS, components, membership, labels and the Dijkstra family (`shortest_path`, `shortest_path_lengths`, `multi_source_shortest_path_lengths`, `eccentricity`). | D3, D17 |
| **One parser, one representation, one adjacency builder** (user decision on review: a special case for two-terminal edges needs a very high benefit). `parse_terminal_edges` reads every edge as a sequence of terminals; while every edge has two terminals (directed: one in, one out) the terminal list stays implicit (edge e at terminals 2e and 2e + 1, the interleaved terminal nodes are the edge list, no offsets), and at the first edge that differs the offsets are written out. `build_adjacency` is one source, instantiated with and without a terminal list like the kernels (D17). Measured against the former separate pair parser: parsing pairs takes the same walltime (20.1–20.3 vs 20.4 ms undirected, 20.0–20.1 vs 20.0 ms directed at 1.25M edges, arm64), the free functions as well (`bfs` 12% faster), and graphs with multi-terminal edges parse 35–40% fewer instructions. The general loop over the terminals of an edge costs instructions the fixed pair loop did not: parsing pairs counts 7–13% more instructions on x86-64, and the union-find kernels one instruction more per edge for the interleaved edge list (+0.5–1.5%); with equal walltime this is accepted as the new baseline (user decision). The free node-id functions parse through it too and reject other than pairs. The only input-specific path left is the `(edge_count, 2)` int buffer, an input format. Kernels that read only two-terminal edges call `require_two_terminal_edges` (O3). | D3, D17, D19 |
| A graph of two-terminal edges keeps its layout and `build_adjacency` exactly. A graph with an edge of other than two terminals adds a terminal list (`terminal_offsets` numbering the terminals of every edge, a two-terminal edge's terminal 0 at its first endpoint and terminal 1 at its second; `terminal_nodes`; `out_terminal_offsets` when directed) and is built by `build_terminal_adjacency`: a two-terminal edge as before, an edge with three or more terminals as `-1 - e` at the node of each of its terminals (directed: in-terminals in the forward lists, out-terminals in the reverse lists) with that slot's terminal in `edge_indices`, and a single-terminal edge with no slot, since it joins nothing. In the edge list every edge of other than two terminals sits at its own index as (node of its first terminal, same node), which union-find joins to itself, so the edge-list kernels need no per-edge test. | D1, D12, D17 |
| One kernel source per algorithm, compiled twice: the BFS loop is an always-inline function with a constant `has_multi_terminal_edges`, instantiated for both values. The instantiation for graphs of two-terminal edges contains no test for negative entries, which keeps its instruction count at `main`'s; the other expands an edge with three or more terminals once per traversal. | D3, D17 |
| A terminal mask is checked only when one is given. A two-terminal edge with a masked terminal joins nothing (case 5), so it is folded into a copy of the edge mask once per call and the loop checks two-terminal edges by edge mask alone; the terminals of an edge with three or more terminals are checked by `terminal_is_active`, entry and exit alike. | D6, D9 |
| One C entry per kernel: `compute_graph_components` and `bidirectional_dijkstra` pick their instantiation from whether the graph has a terminal list, and `first_active_terminal_node` decides membership for both kinds of graph. | D8, D17, D18 |
| One Tarjan search (`tarjan_search` in `biconnectivity.c`) serves bridges, critical edges, critical nodes, blocks and edge labels, instantiated per report mode and per value of `has_multi_terminal_edges`. An edge with three or more terminals is a search state linked to its active terminal nodes; a link is a two-terminal edge or one terminal, so a second terminal at the same node is a back link (case 7). Blocks are closed only below a node, which merges the blocks meeting at a multi-terminal edge (D14); a node is critical only through children whose subtree holds a node (case 3). | D13, D14, D17, case 11 |
| `nodes_on_simple_paths` uses a fifth mode of the same Tarjan search: blocks of the search states themselves, closed below every state, so a multi-terminal edge can separate them as a node does (edge case 15). The entry returns the plain node sets plus, only for blocks holding a multi-terminal edge, their edge indices, so graphs of two-terminal edges build no extra object per block. | D17, edge case 15 |
| Negative terminal weights (D21) keep every search step non-negative: `parse_pass_weights` validates the weights and shifts each edge's entry and exit steps by its lowest terminal weight; an undirected search additionally keeps `ArrivalLabels`, a second label per node and per edge state, so a U-turn or an immediate second pass through the negative terminal can never be taken. Without a negative weight none of this runs. `shortest_path` on an undirected graph with a negative weight searches from both ends with the same labelled step: D21's rules read the same on a reversed path, so the backward side is the forward search run from the target and needs no mirrored labels. A meeting joins a settled far label only, and only when the keys do not conflict (the same arrival edge at a node: a second pass right at its negative terminal; the same terminal at an edge state: a U-turn); a meeting inside an edge state takes off the shift both sides added; and a pass entered at another terminal also meets the far side at the negative terminal's node, because one side represents that pass directly and the other through the edge state. The search stops once the two heap tops add up to the best meeting. Measured on `random_terminals` at 256k nodes against the forward search stopped at the target: farthest node 127–156 ms to 7–8 ms, 10 random pairs 826–929 ms to 49–53 ms (plain weights: 3.3 ms and 32–36 ms). | D17, D21 |
| The C kernels that read only two-terminal edges (quotient edges, reduction) call `require_two_terminal_edges` and raise `NotImplementedError` on a graph with multi-terminal edges themselves, so a direct call into `_core` can never read `-1 - e` as a node. | O3, D13 |
